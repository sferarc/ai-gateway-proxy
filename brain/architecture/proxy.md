# Proxy

`createGatewayProxy(options)` in `src/proxy.ts` returns a handler `(request, context?) => Promise<Response>` with `GET`, `POST`, `PUT`, `DELETE` and `PATCH` properties that point at the same function, so a Next.js route can export them directly (`README.md`).

## Request path

1. Authenticate with [[auth]]. No credential returns 500 with type `authentication_error` and a message naming `AI_GATEWAY_API_KEY` and Vercel OIDC. Every error the proxy raises itself goes through `proxyErrorResponse`, which returns `application/json` in the upstream `GatewayError` shape (`{ error: { message, type } }`), so AI SDK clients can parse it like an upstream error; before this they got plain text.
2. Resolve the upstream path. `extractPath(request)` wins when given; otherwise the catch-all route param named by `segmentsParam` (default `segments`) is joined with `/`; otherwise the path is empty. `extractPath` and `segmentsParam` came in e2e1234 (monorepo #16) so Hono, Express and similar frameworks work without catch-all routes (`CHANGELOG.md` 0.1.0).
3. Build the upstream URL as `baseUrl/path` plus the incoming query string. `baseUrl` defaults to `https://ai-gateway.vercel.sh/v1/ai`. Since #10, `isSafePath` and `buildUpstreamUrl` reject a path that starts with `/`, contains `://`, or has a segment that decodes to `.` or `..` or contains `/`, `\` or NUL, so percent-encoded forms such as `%2e%2e` and `a%2F..` are caught too, as is a segment that fails to decode. The resolved URL must also keep the `baseUrl` origin and path prefix. Any of these returns 400 `invalid_request_error` `Invalid path` before any `fetch` (the `returns 400 without calling fetch` tests under `request handling` in `src/proxy.test.ts`).
4. A `GET` or `HEAD` request (`@ai-sdk/gateway`'s `getAvailableModels()` reads `GET {baseURL}/config`), or any request whose `request.body` is `null`, such as a bodyless `DELETE`, stops here and goes through `forwardBodylessRequest`: it is sent upstream with no body and only the caller's `headers` with `authorization`, `ai-gateway-auth-method` and `ai-gateway-protocol-version`, and the upstream status and body come back unchanged (a 3xx is a 502 as in step 7) with the upstream `content-type` and the allowlisted response headers of step 9. None of the hooks run, since they are typed for `LanguageModelV4CallOptions`, and that includes `onError` on a non-OK status. A thrown fetch goes through the same `proxyFailureResponse` as step 10. Before this, every `GET` returned `400 Invalid JSON body` (tests under `bodyless requests` in `src/proxy.test.ts`, including one that drives `createGatewayProvider({ fetch })` into the handler). A bodyless `DELETE` returned the same 400 until it joined this path (`forwards a DELETE without a body instead of rejecting it as invalid JSON`). A body that reads as the empty string takes this path too: Node adapters such as the README's Express example pass `Readable.toWeb(req)` for every method but `GET` and `HEAD`, so a bodyless `DELETE` arrives with a non-null, empty `request.body`, and it still got the 400 until the handler read the body as text first (`forwards a DELETE whose body is an empty stream, as Node adapters build it`).
5. Parse the body text as JSON (`LanguageModelV4CallOptions`). Invalid JSON returns 400 `invalid_request_error` `Invalid JSON body`.
6. Run `beforeRequest`, which may replace the body. None of the hooks run (`beforeRequest` here, `onError` in step 8, `afterResponse` in step 9) when the incoming request has an `ai-model-id` header and no `ai-language-model-id` header and does not target a `/language-model` path, which is how `@ai-sdk/gateway` 4.x sends every model call but a language model's (embedding, image, video, speech, transcription, reranking, decision, batch start; `getModelConfigHeaders` and `doStartBatch` in its `dist/index.js`). The hooks are typed for `LanguageModelV4CallOptions` and `GatewayResponse`, and an embedding response has `usage: { tokens }`, so an `afterResponse` that read `response.usage.inputTokens.total` threw and every embedding call through the proxy came back as 500 `Error proxying request to AI Gateway` (`runs no hook on an embedding model call from @ai-sdk/gateway` and `runs no onError on a failed call marked with ai-model-id` in `src/proxy.test.ts`). The first version of #47 skipped the hooks on `ai-model-id` alone, and review found that a client could then add that header to a language model call and skip `beforeRequest`, `afterResponse` and `onError`; a request carrying `ai-language-model-id` now runs every hook whatever else it sends (`runs every hook on a language model call that also sends ai-model-id`). `@ai-sdk/gateway` 4.0.116 never sends that combination: `GatewayLanguageModel.getUrl` posts to `/language-model` and `getModelConfigHeaders` always sets `ai-language-model-id` and never `ai-model-id` (`dist/index.js`). That does not settle a hostile client, which controls its own headers, so the rule is on the path as well: a request whose resolved upstream pathname ends in `language-model` runs every hook whatever headers it sends (`LANGUAGE_MODEL_PATH` in `src/proxy.ts`, `runs every hook on the language model path ... that sends ai-model-id alone`). The pathname is first folded by `normalizePathname`: percent-decoded up to three times per segment, lowercased, stripped of `;` parameters, and emptied segments dropped, so `language-model/`, `language-model//`, `language%2Dmodel` and `Language-Model` match too, while `isSafePath` still accepts them. `folds the path ... to a language model call` and `folds the path ... to a batch read and runs no hook` pin further spellings (mixed case, double-encoded, `;` parameters on any segment, repeated slashes), so a change to the fold shows up as a failing test. `BATCH_READ_PATH` matches the same folded form. Spellings the fold does not cover are not enforced. Whether the gateway would serve such a call is not needed to close the hole, and it cannot be observed without a paid call. See [[decisions/2026-10-21-language-model-path-runs-hooks]]. Batch status, results and cancel carry no model header and post only `{ batchId }` (`GatewayBatch.doGetBatchStatus`, `doGetBatchResults` and `doCancelBatch` in its `dist/index.js`), so the header rule ran the hooks on them, and a usage-logging `afterResponse` turned every batch status call into the same 500. A path ending in `batch/status`, `batch/results` or `batch/cancel` (`BATCH_READ_PATH` in `src/proxy.ts`) now runs no hook either (`runs no hook on a batch status or cancel call from @ai-sdk/gateway` and `runs no onError on a failed batch status call`). The match is on the suffix of the resolved upstream pathname, so a `baseUrl` one level up (`.../v1` with path `ai/batch/status`) is still caught. The first version of #52 matched the raw path string, and review found that `buildUpstreamUrl` resolves `?` and `#` as a query or fragment while `isSafePath` allows both, so a path such as `language-model?x/batch/status` (a route param of `language-model%3Fx/batch/status`) reached `/language-model` with every hook skipped. Matching the resolved pathname closes that (`runs every hook on a language model call whose path ... only looks like a batch read`). A client cannot then use it to skip the hooks on a model call, since the gateway serves by path and those paths take no model call.
7. `fetch` upstream with the request's method, the re-serialised body and the headers from `buildRequestHeaders`, layered in three steps. First the caller's `headers`, minus any entry naming the model call. Then an allowlist copied from the incoming request: the model call headers (`MODEL_CALL_HEADER`: `ai-language-model-*`, `ai-model-id`, `ai-*-model-specification-version`), which describe the body the client built, and the request metadata headers (`REQUEST_METADATA_HEADER`: `ai-o11y-*`, `idempotency-key`, `accept`), which override a caller entry of the same name. Last the proxy's own `content-type: application/json`, `authorization: Bearer`, `ai-gateway-auth-method` and `ai-gateway-protocol-version` (`0.0.1`). Each allowlisted header is sent only when the incoming request has it. `@ai-sdk/gateway` 4.x sends `ai-language-model-specification-version: 4` on language model calls and `ai-model-id` plus `ai-<kind>-model-specification-version: 4` on `/embedding-model`, `/image-model` and the other model kinds (`getModelConfigHeaders` in its `dist/index.js`); before this only `ai-language-model-id` and `ai-language-model-streaming` were copied, and both were always sent, so an embedding call reached the gateway with an empty `ai-language-model-id` and no `ai-model-id`. Any other incoming header, including the client's `authorization`, `ai-gateway-*`, `x-vercel-ai-gateway-team`, cookies and `host`, is never forwarded (tests under `request header forwarding` in `src/proxy.test.ts`, including one that drives `createGatewayProvider({ fetch }).embeddingModel(...)` into the handler). Both header paths go through `withGatewayHeaders`, which sets these on a `Headers` built from the caller's `headers`, so a custom header in any casing (`Authorization`, `Content-Type`) is replaced rather than sent alongside; a plain object spread kept both keys and `fetch` joined them as `Bearer user, Bearer gateway` (`keeps gateway headers authoritative over custom headers in any casing` and its `on GET` twin in `src/proxy.test.ts`). Header names in the forwarded record are lowercase. The client's `request.signal` is passed to `fetch`, so a client abort cancels the upstream request (#10; `forwards the client signal and returns 499 when the client aborts` in `src/proxy.test.ts`). On a streamed response, cancelling the transformed stream also cancels the upstream body (#11, `cancels the source when the output stream is cancelled` in `src/stream.test.ts`, [[streaming]]). The upstream `fetch`, here and on the bodyless path, sets `redirect: "manual"`, and a 3xx (or an `opaqueredirect`) returns 502 `proxy_error` `Upstream redirected, the proxy does not follow redirects` without following `Location`, so the gateway bearer token never goes to another host and `onError` does not run ([[decisions/2026-10-21-fail-closed-redirects-and-hook-results]]; `redirects` tests in `src/proxy.test.ts`).
8. On a non-OK status, read the error body as text and parse it as JSON. A body that is not JSON, or is JSON without an `error` object holding a string `message` (`null`, a bare string, `{ "message": ... }`), such as an HTML 502 page from an edge or load balancer, becomes `{ error: { message: "AI Gateway returned <status>: <excerpt>", type: "gateway_error" } }`, with the excerpt whitespace-collapsed and capped at 200 characters; an empty body gives `AI Gateway returned <status> <statusText>`. Before this, the fallback used `statusText` alone, which is empty over HTTP/2, so clients saw `Unknown error`. The result goes to `onError`, which may return a replacement body or a whole `Response` (tests `handles non-JSON error response from gateway`, `names the status ...` and `wraps a JSON error body without an error message` in `src/proxy.test.ts`). An `onError` that returns `undefined` or `null`, as a JavaScript hook that only logs does, is logged once with `console.error` and the error body is forwarded, mirroring `afterResponse` in step 9; before, `undefined` gave an empty body and `null` the literal `null` with the error status, so the client lost the gateway's message (`forwards the upstream error body when the hook returns ...` under `onError hook`). Other non-object results are still serialised as returned.
9. On success, a streamed request (incoming `ai-language-model-streaming: true`) goes through [[streaming]], or returns 500 `proxy_error` `No response body` when upstream sent none; otherwise a response whose `content-type` media type is `text/event-stream` or JSON Lines (`application/x-ndjson`, `application/jsonl`, `application/jsonlines`, `application/x-jsonlines`; `STREAM_CONTENT_TYPE` in `src/proxy.ts`) is passed through as is without `afterResponse`, and any other JSON body goes through `afterResponse` and is re-serialised. An `afterResponse` that returns `undefined` or `null`, which a JavaScript caller can do, is logged once with `console.error` and the upstream body is sent instead, as the streaming path forwards the original `finish` event; before, `undefined` gave an empty 200 body and `null` the literal `null` (pinned by `forwards the upstream body when the hook returns undefined` and `... null` under `afterResponse hook` in `src/proxy.test.ts`). A result that is not an object, or is an array, is rejected: `handleJsonResponse` throws, which step 10 turns into 500 `proxy_error` `Error proxying request to AI Gateway`, instead of serialising it as the body (`returns 500 when the hook returns ...` under `afterResponse hook`). An object with the wrong fields is still not validated. The event stream case is `@ai-sdk/gateway`'s video model: `doGenerate` posts to `/video-model` with `accept: text/event-stream` and no `ai-language-model-streaming`, and reads one `result` or `error` SSE event (`GatewayVideoModel.doGenerate` in its `dist/index.js`). Before this the proxy ran `res.json()` on that body, which threw, so every video generation through the proxy came back as 500 `Error proxying request to AI Gateway` (`passes an event stream through on a request not marked as streaming` and `returns the videos of a video model call from @ai-sdk/gateway` under `streaming` in `src/proxy.test.ts`). The JSON Lines case is `@ai-sdk/gateway`'s batch API: `experimental_batch().doGetBatchResults` posts `{ batchId }` to `/batch/results` and reads `application/x-ndjson`, one result per line (`GatewayBatch.doGetBatchResults` and `createJsonLinesResponseHandler` in `@ai-sdk/provider-utils`). `res.json()` threw on more than one line, so reading batch results through the proxy came back as the same 500 (`passes a JSON Lines body through instead of parsing it as one JSON value` and `returns the results of a batch from @ai-sdk/gateway`). A 200 body of any other type, such as `text/plain`, still goes to `res.json()` and is a 500 when it does not parse (`returns 500 when a successful response body is not JSON`).
   The proxy builds its own response headers for steps 8 and 9: `content-type` plus the upstream headers matching `FORWARDED_RESPONSE_HEADER`: `retry-after`, `retry-after-ms`, `x-ratelimit-*`, `x-vercel-id` and `x-request-id`. The request ids let an operator match a failure to gateway-side logs; `@ai-sdk/gateway` reads `x-vercel-id` as the Vercel request id (`getVercelRequestId` in its `src/vercel-environment.ts`). The rate limit headers let the client back off: `ai`'s `retryWithExponentialBackoffRespectingRetryHeaders` reads `retry-after-ms`, then `retry-after`, from the gateway error's `cause.responseHeaders` and uses that delay when it is under 60 seconds. Before this only `x-vercel-id` was copied, so a 429 through the proxy lost `retry-after` and the client retried on its own exponential schedule. Any other upstream header is dropped, including `set-cookie`, and `content-length` and `content-encoding`, which would be wrong for the re-serialised body. The allowlist applies to the default error response and to a replacement body returned by `onError`; a `Response` returned by `onError` is passed through untouched (tests under `upstream response headers` in `src/proxy.test.ts`, including one that drives `createGatewayProvider({ fetch })` into the handler and reads `retry-after` off the error). [[streaming]] responses get the same headers, and so do bodyless requests (step 4), which keep the upstream `content-type`. Bodyless responses returned only `content-type` until `forwards retry-after and request ids on a bodyless GET` in `src/proxy.test.ts`, so a 429 or failure on `GET /config` lost `retry-after` and the request ids.
10. Any thrown error from step 2 onwards is logged with `console.error("AI Gateway proxy request failed:", error)` and returns 500 `proxy_error` `Error proxying request to AI Gateway`, or 499 with no body and no log when the client has aborted. Only the error object is logged, never the token, body or headers. That includes a throwing `extractPath` or `beforeRequest`, a non-JSON success body and a throwing `afterResponse` or `onError`, which is why the handler `await`s `handleJsonResponse` and `createErrorResponse` inside its `try`: a bare `return promise` lets the rejection escape the `catch` (tests under `error handling` in `src/proxy.test.ts`). A throwing `afterResponse` on a streamed request is logged and the original `finish` event is forwarded unchanged, since the response has already started (`src/stream.ts`, [[streaming]]).

Tests: `src/proxy.test.ts` mocks `fetch` and `@vercel/oidc` and covers each step, the hooks and the HTTP method exports.
