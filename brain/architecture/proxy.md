# Proxy

`createGatewayProxy(options)` in `src/proxy.ts` returns a handler `(request, context?) => Promise<Response>` with `GET`, `POST`, `PUT`, `DELETE` and `PATCH` properties that point at the same function, so a Next.js route can export them directly (`README.md`).

## Request path

1. Authenticate with [[auth]]. No credential returns 500 with type `authentication_error` and a message naming `AI_GATEWAY_API_KEY` and Vercel OIDC. Every error the proxy raises itself goes through `proxyErrorResponse`, which returns `application/json` in the upstream `GatewayError` shape (`{ error: { message, type } }`), so AI SDK clients can parse it like an upstream error; before this they got plain text.
2. Resolve the upstream path. `extractPath(request)` wins when given; otherwise the catch-all route param named by `segmentsParam` (default `segments`) is joined with `/`; otherwise the path is empty. `extractPath` and `segmentsParam` came in 8b8c5ca so Hono, Express and similar frameworks work without catch-all routes (`CHANGELOG.md` 0.1.0).
3. Build the upstream URL as `baseUrl/path` plus the incoming query string. `baseUrl` defaults to `https://ai-gateway.vercel.sh/v1/ai`. Since #10, `isSafePath` and `buildUpstreamUrl` reject a path that starts with `/`, contains `://`, or has a segment that decodes to `.` or `..` or contains `/`, `\` or NUL, so percent-encoded forms such as `%2e%2e` and `a%2F..` are caught too, as is a segment that fails to decode. The resolved URL must also keep the `baseUrl` origin and path prefix. Any of these returns 400 `invalid_request_error` `Invalid path` before any `fetch` (the `returns 400 without calling fetch` tests under `request handling` in `src/proxy.test.ts`).
4. A `GET` or `HEAD` request (`@ai-sdk/gateway`'s `getAvailableModels()` reads `GET {baseURL}/config`), or any request whose `request.body` is `null`, such as a bodyless `DELETE`, stops here and goes through `forwardBodylessRequest`: it is sent upstream with no body and only the caller's `headers` with `authorization`, `ai-gateway-auth-method` and `ai-gateway-protocol-version`, and the upstream status and body come back unchanged with the upstream `content-type`. None of the hooks run, since they are typed for `LanguageModelV3CallOptions`, and that includes `onError` on a non-OK status. A thrown fetch goes through the same `proxyFailureResponse` as step 10. Before this, every `GET` returned `400 Invalid JSON body` (tests under `bodyless requests` in `src/proxy.test.ts`, including one that drives `createGatewayProvider({ fetch })` into the handler). A bodyless `DELETE` returned the same 400 until it joined this path (`forwards a DELETE without a body instead of rejecting it as invalid JSON`).
5. Parse the body as JSON (`LanguageModelV3CallOptions`). Invalid JSON returns 400 `invalid_request_error` `Invalid JSON body`.
6. Run `beforeRequest`, which may replace the body.
7. `fetch` upstream with the request's method, the re-serialised body and the headers from `buildRequestHeaders`, layered in three steps. First the caller's `headers`, minus any entry naming the model call. Then an allowlist copied from the incoming request: the model call headers (`MODEL_CALL_HEADER`: `ai-language-model-*`, `ai-model-id`, `ai-*-model-specification-version`), which describe the body the client built, and the request metadata headers (`REQUEST_METADATA_HEADER`: `ai-o11y-*`, `idempotency-key`, `accept`), which override a caller entry of the same name. Last the proxy's own `content-type: application/json`, `authorization: Bearer`, `ai-gateway-auth-method` and `ai-gateway-protocol-version` (`0.0.1`). Each allowlisted header is sent only when the incoming request has it. `@ai-sdk/gateway` 4.x sends `ai-language-model-specification-version: 4` on language model calls and `ai-model-id` plus `ai-<kind>-model-specification-version: 4` on `/embedding-model`, `/image-model` and the other model kinds (`getModelConfigHeaders` in its `dist/index.js`); before this only `ai-language-model-id` and `ai-language-model-streaming` were copied, and both were always sent, so an embedding call reached the gateway with an empty `ai-language-model-id` and no `ai-model-id`. Any other incoming header, including the client's `authorization`, `ai-gateway-*`, `x-vercel-ai-gateway-team`, cookies and `host`, is never forwarded (tests under `request header forwarding` in `src/proxy.test.ts`, including one that drives `createGatewayProvider({ fetch }).embeddingModel(...)` into the handler). Both header paths go through `withGatewayHeaders`, which sets these on a `Headers` built from the caller's `headers`, so a custom header in any casing (`Authorization`, `Content-Type`) is replaced rather than sent alongside; a plain object spread kept both keys and `fetch` joined them as `Bearer user, Bearer gateway` (`keeps gateway headers authoritative over custom headers in any casing` and its `on GET` twin in `src/proxy.test.ts`). Header names in the forwarded record are lowercase. The client's `request.signal` is passed to `fetch`, so a client abort cancels the upstream request (#10; `forwards the client signal and returns 499 when the client aborts` in `src/proxy.test.ts`). On a streamed response, cancelling the transformed stream also cancels the upstream body (#11, `cancels the source when the output stream is cancelled` in `src/stream.test.ts`, [[streaming]]).
8. On a non-OK status, read the error body as text and parse it as JSON. A body that is not JSON, such as an HTML 502 page from an edge or load balancer, becomes `{ error: { message: "AI Gateway returned <status>: <excerpt>", type: "gateway_error" } }`, with the excerpt whitespace-collapsed and capped at 200 characters; an empty body gives `AI Gateway returned <status> <statusText>`. Before this, the fallback used `statusText` alone, which is empty over HTTP/2, so clients saw `Unknown error`. The result goes to `onError`, which may return a replacement body or a whole `Response` (tests `handles non-JSON error response from gateway` and `names the status ...` in `src/proxy.test.ts`).
9. On success, a streamed request (incoming `ai-language-model-streaming: true`) goes through [[streaming]], or returns 500 `proxy_error` `No response body` when upstream sent none; otherwise the JSON body goes through `afterResponse` and is re-serialised.
   The proxy builds its own response headers for steps 8 and 9: `content-type` plus the upstream `x-vercel-id`, Vercel's request id, so an operator can match a failure to gateway-side logs. `@ai-sdk/gateway` uses the same header name for the Vercel request id (`getVercelRequestId` in its `src/vercel-environment.ts`); it does not read any other correlation header, so `x-request-id` is left out. No other upstream header is forwarded, and a `Response` returned by `onError` is passed through untouched (tests under `upstream correlation headers` in `src/proxy.test.ts`).
10. Any thrown error from step 2 onwards is logged with `console.error("AI Gateway proxy request failed:", error)` and returns 500 `proxy_error` `Error proxying request to AI Gateway`, or 499 with no body and no log when the client has aborted. Only the error object is logged, never the token, body or headers. That includes a throwing `extractPath` or `beforeRequest`, a non-JSON success body and a throwing `afterResponse` or `onError`, which is why the handler `await`s `handleJsonResponse` and `createErrorResponse` inside its `try`: a bare `return promise` lets the rejection escape the `catch` (tests under `error handling` in `src/proxy.test.ts`). A throwing `afterResponse` on a streamed request is logged and the original `finish` event is forwarded unchanged, since the response has already started (`src/stream.ts`, [[streaming]]).

Tests: `src/proxy.test.ts` mocks `fetch` and `@vercel/oidc` and covers each step, the hooks and the HTTP method exports.
