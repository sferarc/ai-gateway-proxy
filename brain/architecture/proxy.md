# Proxy

`createGatewayProxy(options)` in `src/proxy.ts` returns a handler `(request, context?) => Promise<Response>` with `GET`, `POST`, `PUT`, `DELETE` and `PATCH` properties that point at the same function, so a Next.js route can export them directly (`README.md`).

## Request path

1. Authenticate with [[auth]]. No credential returns 500 with type `proxy_error` and a message naming `AI_GATEWAY_API_KEY` and Vercel OIDC. It was typed `authentication_error` until 2026-10-28, and `@ai-sdk/gateway` 4.0.126 answers that type with `GatewayAuthenticationError.createContextualError` (`createGatewayErrorFromResponse` in its `dist/index.js`), which drops the message for advice about the client's own credential: a client with an `apiKey` was told `Invalid API key or token` and to create a new key, though the missing credential is the proxy's. With `proxy_error` the client gets a `GatewayInternalServerError` carrying the proxy's message (`gives a client built on @ai-sdk/gateway the proxy's message when no authentication is available` in `src/proxy.test.ts`). Every error the proxy raises itself goes through `proxyErrorResponse`, which returns `application/json` in the upstream `GatewayError` shape (`{ error: { message, type } }`), so AI SDK clients can parse it like an upstream error; before this they got plain text.
2. Resolve the upstream path. `extractPath(request)` wins when given; otherwise the catch-all route param named by `segmentsParam` (default `segments`) is joined with `/`; otherwise the path is empty. `extractPath` and `segmentsParam` came in e2e1234 (monorepo #16) so Hono, Express and similar frameworks work without catch-all routes (`CHANGELOG.md` 0.1.0).
3. Build the upstream URL as `baseUrl/path` plus the incoming query string. `baseUrl` defaults to `https://ai-gateway.vercel.sh/v4/ai`, the URL `@ai-sdk/gateway` 4.x calls without a `baseURL`; it was `/v1/ai`, the version 2 endpoint, until 2026-10-28 ([[decisions/2026-10-28-default-base-url-v4]]). Since #10, `isSafePath` and `buildUpstreamUrl` reject a path that starts with `/`, contains `://`, or has a segment that decodes to `.` or `..` or contains `/`, `\` or NUL, so percent-encoded forms such as `%2e%2e` and `a%2F..` are caught too, as is a segment that fails to decode. The resolved URL must also keep the `baseUrl` origin and path prefix. Any of these returns 400 `invalid_request_error` `Invalid path` before any `fetch` (the `returns 400 without calling fetch` tests under `request handling` in `src/proxy.test.ts`).
4. A `GET` or `HEAD` request (`@ai-sdk/gateway`'s `getAvailableModels()` reads `GET {baseURL}/config`), or any request whose `request.body` is `null`, such as a bodyless `DELETE`, stops here and goes through `forwardBodylessRequest`: it is sent upstream with no body and only the caller's `headers` with `authorization`, `ai-gateway-auth-method` and `ai-gateway-protocol-version`, and the upstream status and body come back unchanged (a 3xx is a 502 as in step 7) with the upstream `content-type` and the allowlisted response headers of step 9. None of the hooks run, since they are typed for `LanguageModelV4CallOptions`, and that includes `onError` on a non-OK status. A thrown fetch goes through the same `proxyFailureResponse` as step 10. Before this, every `GET` returned `400 Invalid JSON body` (tests under `bodyless requests` in `src/proxy.test.ts`, including one that drives `createGatewayProvider({ fetch })` into the handler). A bodyless `DELETE` returned the same 400 until it joined this path (`forwards a DELETE without a body instead of rejecting it as invalid JSON`). A body that reads as the empty string takes this path too: Node adapters such as the README's Express example pass `Readable.toWeb(req)` for every method but `GET` and `HEAD`, so a bodyless `DELETE` arrives with a non-null, empty `request.body`, and it still got the 400 until the handler read the body as text first (`forwards a DELETE whose body is an empty stream, as Node adapters build it`).
5. Parse the body text as JSON (`LanguageModelV4CallOptions`). Invalid JSON returns 400 `invalid_request_error` `Invalid JSON body`. On a path that runs the language model hooks (step 6), when `beforeRequest`, `afterResponse` or `onError` is set, a body that parses but is not an object (an array, string, number, boolean or `null`; `isRecord` in `src/hook-result.ts`) returns 400 `invalid_request_error` `Invalid request body: a language model call must be a JSON object` before any hook or `fetch`. Before this the hooks received it typed as call options, so a `beforeRequest` reading `request.prompt` on a `null` body threw into step 10's generic 500, and an `onError` could be handed a `request` that was an array. Without those hooks, or on a listed path, such a body is still forwarded unchanged, since the proxy is then a passthrough and the gateway answers it (`returns 400 without running a hook or calling the gateway when the body is ...` and the `forwards a non-object body ...` tests under `request handling` in `src/proxy.test.ts`).
6. Run `beforeRequest`, which may replace the body; a result of `undefined` or `null`, which a JavaScript caller can return, sends the parsed body and logs `beforeRequest hook returned no request, sending the original body`, as `afterResponse` and `onError` do with nothing (`sends the original body when the hook returns ...` in `src/proxy.test.ts`). Before this, `JSON.stringify(undefined)` sent a POST with no body and `null` sent the literal `null`. Any other result that is not an object (a string, number, boolean or array) is logged and returns 500 `proxy_error` `beforeRequest hook returned an invalid request: the result must be an object` without calling the gateway or `onError`; before this it was serialised and sent upstream as the body, and `afterResponse` and `onError` received it as `request` (`returns 500 without calling the gateway when the hook returns ...` in `src/proxy.test.ts`). The fields of an object result are not checked. Since #70's decision, path matching fails closed ([[decisions/2026-10-26-fail-closed-path-matching]]): every hook (`beforeRequest` here, `onError` in step 8, `afterResponse` in step 9) runs unless the upstream pathname relative to `baseUrl` (`relativePath` from `buildUpstreamUrl`) is exactly a member of `NON_LANGUAGE_MODEL_PATHS` or `READ_PATHS` in `src/proxy.ts`. Those are the paths `@ai-sdk/gateway` 4.0.116 posts to for other calls (`getUrl`, `getStartUrl`, `getStatusUrl` and `getBatchUrl` in its `dist/index.js`): `embedding-model`, `image-model`, `video-model`, `video-model/start`, `speech-model`, `transcription-model`, `reranking-model`, `decision-model` and `batch/start`, plus the reads `video-model/status`, `batch/status`, `batch/results` and `batch/cancel`. Headers play no part. The relative path is taken from the resolved URL, so it is still percent-encoded and keeps case, trailing slashes and `;` parameters, and any spelling but the exact one runs the hooks; a `?` or `#` in the route param resolves into the query or fragment, so `language-model?x/batch/status` is the language model path. Tests: `runs no hook on the listed path ...`, `runs every hook on the unlisted path ...`, `runs every hook on ..., which is not exactly a listed path` and `matches the listed paths relative to a custom baseUrl` in `src/proxy.test.ts`. History: #47 skipped the hooks on `ai-model-id` without `ai-language-model-id`, because an `afterResponse` reading `response.usage.inputTokens.total` threw on an embedding response and turned every embedding call into a 500; #52 added the batch read paths; #59 made a path ending in `language-model` run every hook whatever the headers and folded case, percent-encoding and slashes, since a client sets its own headers ([[decisions/2026-10-21-language-model-path-runs-hooks]]). That still left unknown paths with `ai-model-id` and spellings the fold missed without hooks, which the fail-closed list closes. The cost is that a real non-language-model call sent to an unusual spelling, or under a `baseUrl` one level above the client's, runs hooks typed for language model calls. On a path in `NON_LANGUAGE_MODEL_PATHS`, which maps each path to a `ModelCallKind`, `beforeRawRequest` runs instead (see "Raw hooks" below).
7. `fetch` upstream with the request's method, the re-serialised body and the headers from `buildRequestHeaders`, layered in three steps. First the caller's `headers`, minus any entry naming the model call. Then an allowlist copied from the incoming request: the model call headers (`MODEL_CALL_HEADER`: `ai-language-model-*`, `ai-model-id`, `ai-*-model-specification-version`), which describe the body the client built, and the request metadata headers (`REQUEST_METADATA_HEADER`: `ai-o11y-*`, `idempotency-key`, `accept`), which override a caller entry of the same name. Last the proxy's own `content-type: application/json`, `authorization: Bearer`, `ai-gateway-auth-method` and `ai-gateway-protocol-version` (`0.0.1`). Each allowlisted header is sent only when the incoming request has it. `@ai-sdk/gateway` 4.x sends `ai-language-model-specification-version: 4` on language model calls and `ai-model-id` plus `ai-<kind>-model-specification-version: 4` on `/embedding-model`, `/image-model` and the other model kinds (`getModelConfigHeaders` in its `dist/index.js`); before this only `ai-language-model-id` and `ai-language-model-streaming` were copied, and both were always sent, so an embedding call reached the gateway with an empty `ai-language-model-id` and no `ai-model-id`. Any other incoming header, including the client's `authorization`, `ai-gateway-*`, `x-vercel-ai-gateway-team`, cookies and `host`, is never forwarded (tests under `request header forwarding` in `src/proxy.test.ts`, including one that drives `createGatewayProvider({ fetch }).embeddingModel(...)` into the handler). Both header paths go through `withGatewayHeaders`, which sets these on a `Headers` built from the caller's `headers`, so a custom header in any casing (`Authorization`, `Content-Type`) is replaced rather than sent alongside; a plain object spread kept both keys and `fetch` joined them as `Bearer user, Bearer gateway` (`keeps gateway headers authoritative over custom headers in any casing` and its `on GET` twin in `src/proxy.test.ts`). Header names in the forwarded record are lowercase. The client's `request.signal` is passed to `fetch`, so a client abort cancels the upstream request (#10; `forwards the client signal and returns 499 when the client aborts` in `src/proxy.test.ts`). On a streamed response, cancelling the transformed stream also cancels the upstream body (#11, `cancels the source when the output stream is cancelled` in `src/stream.test.ts`, [[streaming]]). The upstream `fetch`, here and on the bodyless path, sets `redirect: "manual"`, and a 3xx (or an `opaqueredirect`) returns 502 `proxy_error` `Upstream redirected, the proxy does not follow redirects` without following `Location`, so the gateway bearer token never goes to another host and `onError` does not run ([[decisions/2026-10-21-fail-closed-redirects-and-hook-results]]; `redirects` tests in `src/proxy.test.ts`).
8. On a non-OK status, read the error body as text and parse it as JSON. A body that is not JSON, or is JSON without an `error` object holding a string `message` (`null`, a bare string, `{ "message": ... }`), such as an HTML 502 page from an edge or load balancer, becomes `{ error: { message: "AI Gateway returned <status>: <excerpt>", type: "gateway_error" } }`, with the excerpt whitespace-collapsed and capped at 200 characters; an empty body gives `AI Gateway returned <status> <statusText>`. Before this, the fallback used `statusText` alone, which is empty over HTTP/2, so clients saw `Unknown error`. The result goes to `onError`, which may return a replacement body or a whole `Response` (tests `handles non-JSON error response from gateway`, `names the status ...` and `wraps a JSON error body without an error message` in `src/proxy.test.ts`). An `onError` that returns `undefined` or `null`, as a JavaScript hook that only logs does, is logged once with `console.error` and the error body is forwarded, mirroring `afterResponse` in step 9; before, `undefined` gave an empty body and `null` the literal `null` with the error status, so the client lost the gateway's message (`forwards the upstream error body when the hook returns ...` under `onError hook`). Any other result that is not a `Response` goes through `gatewayErrorProblem` (`src/hook-result.ts`): one that is not an object with an `error` object holding a string `message` and a string or absent `type`, the fields `@ai-sdk/gateway`'s `gatewayErrorResponseSchema` requires, is logged as `onError hook returned an invalid error, forwarding the upstream error body: <problem>` and the error body is forwarded. Before, such a result was serialised as returned, and the client failed to parse it and reported `Invalid error response format` instead of the gateway's message (`forwards the upstream error body when the hook returns ...` and `gives a client built on @ai-sdk/gateway the upstream message when the hook result is invalid` under `onError hook`). It falls back rather than answering 500 like `afterResponse` in step 9, because the error status and its `retry-after` already tell the client what happened.
9. On success, a streamed request (incoming `ai-language-model-streaming: true`) goes through [[streaming]], or returns 500 `proxy_error` `No response body` when upstream sent none; otherwise a response whose `content-type` media type is `text/event-stream` or JSON Lines (`application/x-ndjson`, `application/jsonl`, `application/jsonlines`, `application/x-jsonlines`; `STREAM_CONTENT_TYPE` in `src/proxy.ts`) is passed through as is without `afterResponse`, and any other JSON body goes through `afterResponse` and is re-serialised. An `afterResponse` that returns `undefined` or `null`, which a JavaScript caller can do, is logged once with `console.error` and the upstream body is sent instead, as the streaming path forwards the original `finish` event; before, `undefined` gave an empty 200 body and `null` the literal `null` (pinned by `forwards the upstream body when the hook returns undefined` and `... null` under `afterResponse hook` in `src/proxy.test.ts`). Any other result goes through `gatewayResponseProblem` (`src/hook-result.ts`), and one with a missing or wrong-typed field is rejected: `handleJsonResponse` logs and returns 500 `proxy_error` `afterResponse hook returned an invalid response: <problem>` instead of serialising it (`returns 500 naming the problem when the hook returns ...` under `afterResponse hook`). The check covers `content` (objects with a string `type`), `finishReason` (string `unified`, string or absent `raw`), `usage` (absent, or `inputTokens` and `outputTokens` objects with number or absent counts), `warnings` (absent or an array, since `@ai-sdk/gateway` defaults it) and `providerMetadata` (absent or an object); `null` counts as absent because the body is JSON (`forwards a hook result with ...`). Before #70's decision, a non-object or array result was a generic 500 and an object with wrong fields was forwarded as returned ([[decisions/2026-10-26-strict-after-response-results]]). The event stream case is `@ai-sdk/gateway`'s video model: `doGenerate` posts to `/video-model` with `accept: text/event-stream` and no `ai-language-model-streaming`, and reads one `result` or `error` SSE event (`GatewayVideoModel.doGenerate` in its `dist/index.js`). Before this the proxy ran `res.json()` on that body, which threw, so every video generation through the proxy came back as 500 `Error proxying request to AI Gateway` (`passes an event stream through on a request not marked as streaming` and `returns the videos of a video model call from @ai-sdk/gateway` under `streaming` in `src/proxy.test.ts`). The JSON Lines case is `@ai-sdk/gateway`'s batch API: `experimental_batch().doGetBatchResults` posts `{ batchId }` to `/batch/results` and reads `application/x-ndjson`, one result per line (`GatewayBatch.doGetBatchResults` and `createJsonLinesResponseHandler` in `@ai-sdk/provider-utils`). `res.json()` threw on more than one line, so reading batch results through the proxy came back as the same 500 (`passes a JSON Lines body through instead of parsing it as one JSON value` and `returns the results of a batch from @ai-sdk/gateway`). A 200 body of any other type, such as `text/plain`, still goes to `res.json()` and is a 500 when it does not parse (`returns 500 when a successful response body is not JSON`). A 204 or 205 is checked first, ahead of the streaming branch: it is forwarded with a null body, no `content-type` and the allowlisted headers below, and `afterResponse` does not run, while `afterRawResponse` still receives it on a listed path. Before this, a non-streamed one went to `res.json()`, which threw on the empty body, and a streamed one with `afterResponse` hit `No response body`, so both came back as a 500; `new Response` also refuses a body with either status (`successful responses without a body` in `src/proxy.test.ts`). Whether the gateway sends either status is unknown: every `successfulResponseHandler` in `@ai-sdk/gateway` 4.0.126 reads a body, so this covers a `baseUrl` pointed at another service or a future gateway route rather than a current client call.
   The proxy builds its own response headers for steps 8 and 9: `content-type` plus the upstream headers matching `FORWARDED_RESPONSE_HEADER`: `retry-after`, `retry-after-ms`, `x-ratelimit-*`, `x-vercel-id` and `x-request-id`. The request ids let an operator match a failure to gateway-side logs; `@ai-sdk/gateway` reads `x-vercel-id` as the Vercel request id (`getVercelRequestId` in its `src/vercel-environment.ts`). The rate limit headers let the client back off: `ai`'s `retryWithExponentialBackoffRespectingRetryHeaders` reads `retry-after-ms`, then `retry-after`, from the gateway error's `cause.responseHeaders` and uses that delay when it is under 60 seconds. Before this only `x-vercel-id` was copied, so a 429 through the proxy lost `retry-after` and the client retried on its own exponential schedule. Any other upstream header is dropped, including `set-cookie`, and `content-length` and `content-encoding`, which would be wrong for the re-serialised body. The allowlist applies to the default error response and to a replacement body returned by `onError`; a `Response` returned by `onError` is passed through untouched (tests under `upstream response headers` in `src/proxy.test.ts`, including one that drives `createGatewayProvider({ fetch })` into the handler and reads `retry-after` off the error). [[streaming]] responses get the same headers, and so do bodyless requests (step 4), which keep the upstream `content-type`. Bodyless responses returned only `content-type` until `forwards retry-after and request ids on a bodyless GET` in `src/proxy.test.ts`, so a 429 or failure on `GET /config` lost `retry-after` and the request ids.
10. Any thrown error from step 2 onwards is logged with `console.error("AI Gateway proxy request failed:", error)` and returns 500 `proxy_error` `Error proxying request to AI Gateway`, or 499 with no body and no log when the client has aborted. Only the error object is logged, never the token, body or headers. That includes a throwing `extractPath` or `beforeRequest`, a non-JSON success body and a throwing `afterResponse` or `onError`, which is why the handler `await`s `handleJsonResponse` and `createErrorResponse` inside its `try`: a bare `return promise` lets the rejection escape the `catch` (tests under `error handling` in `src/proxy.test.ts`). A throwing `afterResponse` on a streamed request is logged and the original `finish` event is forwarded unchanged, since the response has already started (`src/stream.ts`, [[streaming]]).

## Raw hooks

`beforeRawRequest` and `afterRawResponse` (`src/types.ts`) are the hooks for the calls the language model hooks skip, added on the owner's #70 decision as new optional hooks so the existing hook signatures did not change. They run only on a request with a body whose relative path is in `NON_LANGUAGE_MODEL_PATHS`, never on `READ_PATHS` or bodyless requests. The context is `{ kind, path, modelId, request }`: `kind` comes from the path, `modelId` from the incoming `ai-model-id` header (an embedding or image body does not name its model), and `request` is the parsed body as `unknown`.

- `beforeRawRequest` runs after JSON parsing and before `fetch`. A result other than `undefined` or `null` replaces the body; both of those send the parsed body, as `beforeRequest` does in step 6 but without the log, since returning nothing is the documented way to leave the body alone. Before this, `null` was sent upstream as the literal `null` body (`sends the parsed body when beforeRawRequest returns ...` in `src/proxy.test.ts`). Other results, including strings and arrays, are sent as returned, since the hook is untyped.
- `afterRawResponse` runs after `forwardUpstreamResponse` builds the client response, on success and on error statuses, so it sees exactly what the client would get, including the `parseErrorBody` fallback on a non-JSON error and a video call's event stream. It does not run on the 502 redirect refusal or when `fetch` throws. `applyAfterRawResponse` sends a returned `Response`; for `undefined` or `null` it sends the built response, unless `response.bodyUsed`, which throws, since forwarding a consumed body would fail at send time. Any other result throws. Throws become step 10's 500. When the hook returns another `Response`, throws or returns an invalid result, `discardUnreadBody` cancels the built response's body unless it is used, locked (read or piped) or is the returned `Response`'s own body, as with `new Response(response.body, init)`. Before this the body was left unread, which for a video call's event stream kept the upstream request open after the client got the replacement or the 500, since an unread fetch body holds its connection until garbage collection (`cancels the upstream body when afterRawResponse ...` and `keeps the upstream body when the replacement Response ...` under `raw hooks` in `src/proxy.test.ts`). A replacement that reads `response.body` lazily from a `pull` callback, without locking it first, gets a cancelled stream; the hook is expected to read `response.clone()` or wrap the body directly.

The hook gets the response itself rather than a clone, because an unread `clone()` tees the body and buffers whatever the slower branch has not read, which for a large `batch/start` or video body is the whole of it. Tests: `raw hooks` in `src/proxy.test.ts` and `runs the raw hooks on a batch start ...` in `src/non-language-model.test.ts`.

## Calls that do not reach the handler

Read in `@ai-sdk/gateway` 4.0.126 `dist/index.js`; not pinned by a test, and not observed against the real gateway.

- `GatewayTranscriptionModel.doStream` and `GatewaySpeechModel.doStream` open a WebSocket through `connectToWebSocket` at `toGatewayTranscriptionUrl` or `toGatewaySpeechUrl`: `baseURL` with `http` swapped for `ws`, plus `/transcription-model` or `/speech-model` and `?ai-model-id=`, with the client's bearer token in `Sec-WebSocket-Protocol`. The handler takes a `Request` and returns a `Response`, so it cannot answer an upgrade. Their `doGenerate` posts JSON to the same paths and is handled as in step 6.
- `getCredits`, `getSpendReport` and `getGenerationInfo` build their URL from `new URL(baseURL).origin` (`/v1/credits`, `/v1/report`, `/v1/generation`), so through a proxy they go to the proxy's host outside its route.

Both are listed under Client in `README.md`. Carrying either is a contract choice for the owner ([[plans/roadmap]]).

Tests: `src/proxy.test.ts` mocks `fetch` and `@vercel/oidc` and covers each step, the hooks and the HTTP method exports.
